- 起因：任务都走 magpie 的路由组（如 `group/smart`、`group/fr-smart`），会话里只显示组名，看不出这一轮落到哪个成员模型。要查是谁答的、花的谁的钱时，只能另开终端翻网关日志。

## 一、提出的问题

### 1. 会话里只显示路由组，看不出实际成员

- **现象**：Mirasim 和 fleet-ade 的会话都只显示配置里选的那一个名字（`magpie/group/fr-smart`、`group/smart` 这类）。网关确实选了具体成员，但这个事实没有到达界面（**实测** 见第二节）。
- **根因**：链路上没有任何一层用正式字段承载「这一轮实际用了谁」。
  - 网关的 OpenAI 兼容回包里 `model` 回显请求里的别名；成员只在 `X-Magpie-Model` / `X-Magpie-Provider` 响应头里（**实测**）。
  - 嵌套组只暴露下一跳：本地 `group/fr-smart` 的头写 `france/group/smart`，不写最终成员（**实测**）。
  - ACP 协议里只有 `modelId`（会话配置项），没有「实际模型」字段；omp 上报的就是配置里的别名（**实测**）。
  - fleet-ade 的契约里没有 served/actual model 一类字段（**按代码** `packages/contracts/src` 全量搜索无此概念）。
- **需求方的思路**：先只读查清回包、用量记录、三个界面各显示什么，再定改法。
- **判断**：成立。这不是 fleet-ade 界面的缺口；补界面前得先把事实从某一层带上来。改在哪一层，是第五节要拍的。
- **做法**：见第五节。
- **不做什么**：本单不改代码，不改网关行为。

## 二、另外查出来的

### 网关回包：body 是别名，成员在响应头（实测）

本机 `POST /v1/chat/completions`，`model: group/smart`，非流式：

- 回包 JSON 的 `model` 是 `"group/smart"`，和请求一字不差。
- 响应头：`X-Magpie-Model: grok/grok-4.7@500k`、`X-Magpie-Provider: grok`、`X-Request-Id: <id>`。

同一条请求在 `magpie usage --csv` 里的对应行（按 `request_id` 对上）：

- `requested_model=group/smart`、`model=grok-4.7@500k`、`served_model=grok-4.7-build`、`provider=grok`、`host=cli-chat-proxy.grok.com as …`、`session` 列是调用方报的会话 id（`curl` 发的为空，omp 发的有值）。

结论：成员只在非标准响应头和用量记录里；body 永远是别名。

### 流式：成员同样只在响应头，先于首块到达（实测）

同一条请求加 `stream: true`：每个 chunk 的 `model` 都是 `"group/smart"`，首块不带成员；`X-Magpie-Model: grok/grok-4.7@500k` 在响应头里，比首个 SSE 块早到。也就是说，流式场景不需要等到最后一块才能知道成员，但只能从响应头读。

### 嵌套组只带下一跳（实测）

本机 `model: group/fr-smart`（成员依次是 `france/group/smart`、`group/smart`）：回包 `model` 仍是 `"group/fr-smart"`，响应头是 `X-Magpie-Model: france/group/smart`、`X-Magpie-Provider: france`。

本地这一跳把请求交给了法国网关，法国网关自己选中的成员（实测为 `grok/grok-4.7@500k`）没有回传上来。本地用量行同样是 `model=group/smart`、`served_model=group/smart`，不是最终成员。

### 法国网关的行为与本机一致（实测）

WireGuard 内直打法国网关（只读一次，非流式，`model: group/smart`）：回包 `model` 为 `"group/smart"`，头 `X-Magpie-Model: grok/grok-4.7@500k`、`X-Magpie-Provider: grok`。两边是同一套约定，没有谁多做一步。

### 用量记录能按请求或会话对上本地这一跳（实测）

`magpie usage --csv` 的列里有 `request_id`、`session`、`requested_model`、`provider`、`host`、`model`、`served_model`、`tokens`、`cost_usd`、`status`。omp 发的请求 `session` 列有值，可以直接和会话对上；单条请求用 `request_id` 对。上限是：它只记经过本机的这一跳，嵌套组时记的是别名，最终成员要看法国那份网关的用量。

### omp 经 ACP 只报别名（实测）

`omp acp` 握手后 `session/new` 返回的会话配置里，`model` 这一项：

- `currentValue` 是 `magpie/group/fr-smart`（本会话用的那个）。
- 共 168 个可选值，全是 `magpie/<provider>/<模型或组>`；组条目名是「工程组 · routing group」这类显示名，描述就是 id。
- 没有任何字段表示「这一轮实际落到谁」。

### fleet-ade 的显示链路（按代码）

- provider 能力里的模型清单来自 agent 上报：ACP 的模型配置项或会话 model state（`packages/provider-acp-registry/src/server/probe.ts:180-197`）。
- 本轮报给界面的是 agent 回报的选择：`packages/provider-acp/src/server/adapter.ts:7433`（发请求时用 `modelSelection.model`）、`8421-8452`（写进 `nativeMetadata`）。
- 界面「当前模型」取 `providerThread.nativeMetadata.modelSelection`：`packages/client-runtime/src/state/threadExecution.ts:211-218`（`deriveReportedModelSelection`）。显示在输入框的模型控件上（`apps/web/src/components/chat/ComposerModelEffort.tsx:92-101`、`TraitsPicker.tsx:351`）。
- 每轮的 token 用量有单独的快照并显示（`apps/web/src/components/ChatView.tsx:539`、`2530`），模型名没有对应物。
- 关键一点：ACP 模式下 fleet-ade 不在 HTTP 链上，请求是 omp 发的，网关的响应头 fleet-ade 根本看不到（**按代码** 上述链路）。想让它显示，只能由 omp 经 ACP 报上来，或者去读网关的用量。

### Mirasim 与会话记录（实测）

- omp 会话本身记的是配置值（本会话 `magpie/group/fr-smart`），它上面的网关选择没有落到会话记录里。
- Mirasim 的 `~/.mirasim/setting.json` 只存模型目录与会话按启动时选的模型；`usage-readings.json` 目前是空的（`[]`），没有按请求记的实际成员。
- **推断**：Mirasim 界面显示的也是别名。要显示实际成员，同样得等某一层把它带上来，而不是 Mirasim 自己算。

## 五、要拍板的

1. **把事实从哪一层带上来**：建议方案乙（网关在回包里新增成员字段，并在嵌套组时回传上游成员）。备选方案甲（omp 经 ACP 报每轮实际成员）和方案丙（界面旁路读网关用量）。不定则谁都做不了。
2. **显示到什么程度**：建议只在「这一轮」上加一处：hover 或详情里看到 `grok/grok-4.7@500k`（以及经法国时看到最终成员）。备选：常驻在会话标题或每轮消息上；或不改界面，只让用量页能查。不定则实现会做成一处多余的位置。
3. **是否接受非标准字段**：建议接受一个显式的非标准字段（如 `X-Magpie-Model` 已在头里，body 加 `magpie_model`），不改 `model` 的语义。备选：把 `model` 改成实际成员，风险是有些客户端按 `model` 匹配别名、会误判切换。不定则可能改坏现有客户端。

### 方案甲：omp 经 ACP 报每轮实际成员

omp 在收到网关响应头后，把成员写进 ACP 的会话更新元数据；fleet-ade 在适配器里读出来，作为一个新字段显示。

- 好处：fleet-ade 改动小（多一个字段加一处显示），Mirasim 也能用同一份数据。
- 代价：要在 omp 侧改；不经过 omp 的直连客户端（claude、codex）仍然看不到。ACP 的元数据字段要协商，否则老客户端忽略。
- 改动量：omp 一处发、fleet-ade 一处收一处显示，加契约字段与测试。
- 风险：ACP 元数据是扩展位，别的 agent 不认；omp 升级不同步时显示为空，需要按「无数据」处理。

### 方案乙：网关回包带成员，嵌套组回传上游（推荐）

magpie 在回包里新增 `magpie_model`（非流式在根、流式在每块或首块），并把自己从上游 `X-Magpie-Model` 读到的成员继续往上传；`model` 字段语义不动。

- 好处：一处改，所有客户端和所有界面都受益；嵌套组也能一路带上来；用量记录与回包对得上。
- 代价：magpie 要改；客户端要各自读新字段（fleet-ade 走 ACP 时仍需 omp 转一手，所以它和方案甲是叠加关系而不是二选一）。
- 改动量：magpie 一处，fleet-ade 若经 ACP 还需 omp 转报（见甲）。
- 风险：多一个非标准字段要维护；旧客户端忽略它，不会有兼容问题。

### 方案丙：界面旁路读网关用量

不动链路，界面按会话 id 去查 `magpie usage` 的 API，把实际成员显示在会话上。

- 好处：不改协议，不动 omp。
- 代价：依赖网关在本机可访问、用量写入延迟；嵌套组时本地用量只有别名，最终成员要查法国那份；跨机器（远程连一个环境）时路径更长。
- 改动量：服务端一个查询加界面一处显示。
- 风险：用量是事后记录，实时会话里会短暂空白或滞后；密钥与网关地址要进配置。不推荐，除非前两个都不可行。
