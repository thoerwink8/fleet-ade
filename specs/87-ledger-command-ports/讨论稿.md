缺的三块（都不在命令本身的协议里，但挡着「换地址就能接上」）：

1. **发不出机器通行证**。`node_keys` 只有测试里直接插行（`nodeReads.test.ts:32`、`:351`，`notes.test.ts:39`），fleet-ade 没有发证/吊销的命令或接口（按代码，`apps/server/src/cli/` 下没有 ledger 相关子命令）。没有任何证时，节点证路由一律 503 `node_keys_not_wired`（`notes.ts:269-271`）。
2. **仓登记只有一个来源**。领单和过程记录都要求仓在 `repos` 表里（`nodeClaims.ts:114-119`、`notes.ts:281-296`），而这表只由流水线启动时按白名单登记（`pipeline/claimLease.ts:137-145`，调用点 `pipeline/PipelineRuns.ts:612`、`:819`）。命令侧的仓不在白名单里就 404 `unknown_repo`。
3. **配置没有 ADE 版**。命令只认 `~/.fleet-dao/local-sessions/config.json` 的 `url` + `token`（fleet-dao `packages/conventions/src/work.ts:81-95`），fleet-ade 侧的部署文档（`docs/operations/france-headless.md`）没有账本接口、数据文件位置和这一份配置的任何说明。

### 2. 「稳定契约」的边界在哪

- 命令侧对 GET 租约的口是**严格四字段**（旧命令 `parseFranceClaims` 用 `exactKeys`，fleet-dao `work-queue.ts:118-155`）。ADE 已经对齐（`nodeReads.ts:286-293`），所以以后给租约读口加字段会直接把所有旧命令打回「认不出」。这条要写进 ADE 的接口说明。
- 写口失败形状两边不同：旧命令只读 `error.message`（fleet-dao `work.ts:298-311`），ADE 回 `{error:{code,message}}` + HTTP 状态（`nodeReads.ts:347-356`），可用；旧系统还有 `{ok:false,code,why}` 的成功态变体（fleet-dao `shared/src/local-claims.ts:74-86`），命令不读，不挡事。
- 旧系统在领单成功里回 `taskId`，ADE 没有（`nodeReads.ts:358-363`）；命令侧全仓没有读它（按代码，`work.ts`、`work-queue.ts` 搜不到 `taskId`）。
- 事件读口 ADE 多回一个 `next`（`notes.ts:411`），旧命令只解析 `events` 数组（fleet-dao `ledger-read.ts:110-116`），兼容。

### 3. 迁完之后，旧后端怎么停

照 fleet-dao 决定 0126、`specs/3979-ade-merge/账本迁移盘点.md` 第七节：双写对账 → 切读 → 命令连续 7 天零失败 → 停旧后端 → 停后 72 小时正常 → 旧库保留 30 天再归档。备份不得低于 7 天 + 4 周并每周真恢复演练（同文档第六节）。本单只需要把「命令侧这段」的验收点写实。

## 二、另外查出来的

### 租约写口少了「结束记录」（按代码）

`finish` 只删行，`outcome`（done/failed/released）和 `reason` 校验完就丢（`nodeClaims.ts:121-131`）。旧系统在同一个事务里改任务状态并记一条操作记录（盘点文档第二节第 6 行）。对命令侧没影响（`work done` 只看 200/409），但队列之外再想回答「这单是做完还是放手」就查不到了。**推断**：迁移期先不动，需要时另开单在 `audit_log` 记一条，不塞进租约表。

### 一把证管所有口，范围只有「哪台机器」（按代码）

- 头是 `X-Fleet-Node-Token`（`notes.ts:19`），只存 sha256、定长比较（`notes.ts:194-209`）；证过长或为空直接不认（`:37`、`:198`）。
- 同一个校验函数给 `report`、`sessions`、`claims`、`notes`、`events` 用（`nodeReads.ts:77-80` 调 `notes.ts:258-279`）；没有作用域、没有「只读」和「可写」之分。
- 驾驶舱读口（`GET /api/nodes`、`/api/nodes/sessions`、`/api/nodes/:nodeId`）另走登录 + `orchestration:read`（`nodeReads.ts:397-413`，契约 `packages/contracts/src/auth.ts:31`），不认节点证。命令侧要的口全在节点证这一侧，所以不需要给机器发用户级凭据。

### 数据在哪个文件、谁来备份（按代码）

- 账本是独立文件：`<stateDir>/ledger.sqlite`（`notes.ts:474`），`stateDir` = `baseDir/userdata`，dev 是 `baseDir/dev`（`apps/server/src/config.ts:158-162`）。法国无界面部署把 `baseDir` 指到自己的数据目录（`docs/operations/france-headless.md` §2），所以账本落在那个目录的 `userdata/` 下。
- 现在的部署脚本只备份发行物（`scripts/deploy/france-update.sh:47` 的临时备份），**没有任何数据备份**；fleet-ade 也没有备份文档。
- `statev2.sqlite`（会话、项目、设置）和 `ledger.sqlite`（钥匙、快照、租约、事件）是两个文件，快照要同一次读，否则租约和会话对不上。

### 事件读口的容量口径（按代码）

`GET /api/nodes/events` 走 `audit_log_ledger_events_idx`（`notes.ts:245-247`），查询是 `id > after AND (target GLOB 'issue:*' OR target GLOB 'progress:*') ORDER BY id LIMIT limit`（`notes.ts:374-379`），读的行数与返回行数成正比，与账本总量无关；`limit` 超上限按 500 截（`notes.ts:188`）。旧命令按 500 一页翻、最多 500 页（fleet-dao `ledger-read.ts:24-28`），两边一致。

### 现有测试证明了什么（按代码）

- 租约：过期不返回、四字段、无 `executor/state/fencing`（`nodeReads.test.ts:169-204`）；库读失败 503 且无 `claims` 键（`:206-224`）；无证/错证 401（`:241-260`）。

- **没有**一条测试让同一把证、同一台服务器同时读租约和事件；也没有任何测试打真实的 HTTP 监听。单的验收项「一条只读的对接测试」目前只是两个内存路由测试（**推断**：不算完全达成）。

## 五、要拍板的

讨论中。每条给两个以上选项，推荐写在条目前。

1. **配置读哪一份 —— 推荐 A。**
   - A（推荐）：新增 `~/.fleet-ade/ledger.json`（`0600`，`{url, token}`），命令先读它，读不到再读旧路径 `~/.fleet-dao/local-sessions/config.json`，并在输出里说用的是哪一份。好处：从 fleet-dao 迁来的机器只改地址就能接上（旧文件还在，兼容期自然覆盖）；旧目录退役后不留尾巴；出问题能一眼看出读的是哪份。代价：fleet-base 要写两处读取和一条「用了哪份」的提示。
   - B：沿用旧路径不动，迁移期只改里面的 `url`。最省一次改动，但旧目录跟 fleet-dao 一起退役时还得再迁一次，且文件名会长期指着已经不存在的东西。
   - C：只用环境变量（`FLEET_ADE_URL`、`FLEET_ADE_NODE_TOKEN`）。适合常驻进程，不适合每台机器的交互命令；token 进 shell 历史和环境快照的风险更高。

2. **命令用什么身份 —— 推荐 A。**
   - A（推荐）：机器通行证，头 `X-Fleet-Node-Token`，与服务端现有实现完全一致（`notes.ts:258-279`）；一机一证、可单独吊销、不碰用户登录态。
   - B：配对得到的用户级 bearer 令牌 + `orchestration:read`。要按人分发凭据到每台机器，吊销粒度是「这个人所有机器」；而且现在的 `claims/notes/events` 路由不认它，要改认证。
   - C：一份共用的静态密钥。最省，但无法按机器吊销、出事分不清是哪台。

3. **通行证怎么发和吊销 —— 推荐 A。**
   - A（推荐）：加 `t3 ledger node-key new|list|revoke`，明文只在 `new` 打印一次，库里存 sha256，吊销写 `revoked_at`（照旧系统 `fleet-api node-key new` 的做法，表结构已支持）。理由：装机器和换机器是日常动作，没有命令就只能手改库。
   - B：手工往 `ledger.sqlite` 插行。零开发，但会绕开校验（哈希形状）和审计，容易插错。
   - C：在 ADE 界面里发证。要多做页面和权限模型；现在没有「谁是管理员」的概念，先不做。

4. **仓登记从哪来 —— 推荐 A。**
   - A（推荐）：服务端启动时按 settings 的仓清单登记（流水线白名单 + 一份命令侧仓清单），沿用 `INSERT OR IGNORE`（`claimLease.ts:137-145`）。不新增 HTTP 面，登记结果看表即可。
   - B：新加 `POST /api/nodes/repos`（节点证）让命令自己登记。多一个写口、多一套校验和审计；命令每个仓都要跑一次初始化。
   - C：不校验登记。与旧规矩「未登记仓一律拒绝」冲突，且会让拼写错的仓悄悄写进另一本账。

5. **租约时长和结束语义 —— 推荐 A。**
   - A（推荐）：照旧 2 小时、显式 `work renew`、`finish` 删行。命令侧零改动，失败码已经对齐；死会话最长挡 2 小时（旧系统也有这个窗口，靠心跳和开着的 PR 顺延来兜）。
   - B：缩到 30 分钟，命令每次跑都续。死会话让位快，但 fleet-base 必须每次调用都续，漏一次就可能在干活中途丢租约，出现两个人同时做。
   - C：服务端按心跳或开着的 PR 自动顺延。最贴近旧系统，但 ADE 现在没有读心跳/PR 的后台任务，要新做一块并防抖。
   - 附带（不单独拍）：`outcome`/`reason` 现在不落库。建议这一轮不加，另开单在 `audit_log` 记一条，不塞进租约表。

6. **过程记录写哪、进度流水落在哪 —— 推荐 B。**
   - A：只写 ADE 账本，不再贴评论。机器读得顺，但人看进度得开 ADE；fleet-base 现在也没有放评论的单。
   - B（推荐）：在 fleet-base 开一张置顶进度单，照旧贴评论给人看；同时写 ADE 的 `notes` 给机器和对账。好处：保留现在的阅读习惯，账本的对账也有数据；代价：两处写，评论失败不挡账本、账本失败不挡评论（照旧规矩）。
   - C：只贴评论，不写账本。最省，但账本的对账和 `GET /api/nodes/events` 就没有新数据，迁移「切读」这一步无从验证。

7. **原话私有库放哪 —— 推荐 A。**
   - A（推荐）：ADE 加 `POST /api/nodes/quotes`（节点证），收 `{id, spokenAt, text, machine, lineage, remote, directiveId}`，存进账本（单独表），不进仓、不回显、不写日志。旧驾驶舱私有库的字段照搬（fleet-dao `packages/db/src/schema/private-quotes.ts`）。
   - B：迁移期继续 SSH 打旧驾驶舱私有库。省事，但旧后端 30 天后停，这条路就断，还得再迁一次。
   - C：原话只留本机 `~/.fleet-dao/private/quotes/`。最简单，但换机器就查不到，且「原话可回查」这条保证降级。

8. **迁移期谁为准、历史怎么导 —— 推荐 A + 保留 id。**
   - A（推荐）：双写。命令写 ADE 一份、旧库一份；读租约时两处都读、合并（旧库的行只有旧引擎会写，ADE 只有命令和流水线会写），差异记成对账报告。切读判据：同一把证、同一时刻两处租约集合与事件 id 段一致，连续 7 天零失败。
   - B：立刻 ADE 单写。旧引擎仍按自己的库派单，两边会同时做同一张单。
   - C：旧库单写、ADE 只读。等于没迁，只是多了一处读口。
   - 历史导出：保留旧 `audit_log.id` 原样导入（否则每台机器的本机游标都要重设，易漏）；`node_keys` 搬 `node_id`、`token_hash`、`revoked_at`；`node_reports`/`node_sessions` 搬 `payload` + `received_at`；`tasks` 只搬 `executor=local` 且未过期的租约；导完先用 `GET /api/nodes/events?after=0&limit=1` 和租约读口核对行数与最大 id。备选：重新编号并同步重设游标（多一步、易漏）；不导历史（`directive-export` 和旧事件回查全部作废，不推荐）。

9. **备份和恢复演练做到哪 —— 推荐 A。**
   - A（推荐）：每晚 restic 备份整个 ADE 数据目录（`statev2.sqlite`、`ledger.sqlite`、`settings.json`、`secrets/`），7 日 + 4 周，每周在临时目录真恢复一次并核对每表行数、最大 `audit_log.id`、有效钥匙数；恢复到临时目录后再删。与旧库的备份合同同档（盘点文档第六节），但不共用一份仓。
   - B：只备份 `ledger.sqlite`。小、快，但丢会话和设置，恢复后要重新配对。
   - C：沿用旧库备份。机器和引擎都不同，旧库停了以后只剩历史，救不了 ADE。

## 七、没核实的

- 法国线上的真实库存：钥匙数、租约条数、事件行数、请求量、最近的备份和恢复结果都没查（没连生产）。
- 现在有几台机器在用命令侧：只看过代码和文档，没有逐机清点；「连续 7 天零失败」按哪几台算要等清单。
- 旧系统自动顺延租约（心跳、开着的 PR）的确切判法和边界：只读了 `work-queue.ts` 的注释与 `tasks` 表结构，没读引擎里的顺延实现。
- `progress note` 在 fleet-base 要落到哪张单：fleet-base 仓里没有置顶进度单，本单只给了选项，没有指定具体单号。
- 一条只读对接测试用真实监听进程还是内存路由：现有测试都是内存路由，真实 HTTP 口的行为（超时、连接拒绝）没测过。
- 旧驾驶舱私有库的现有原话条数和最老的记录时间：没有只读连接，没法判断迁不迁历史原话。
