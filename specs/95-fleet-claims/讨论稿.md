## 二、根因

1. **互斥只在本机生效。** 流水线绕过 `/api/nodes/claims` 直接写本机库，跨机那条路没有任何调用者。两台机器各自的 `node_claims` 都空着，谁都不知道对面在做什么。
2. **租约是 2 小时且不续期。** `renew` 动作写好了但流水线一次都没调过（**按代码**）。中断要等两小时才从账本上看出来，实际上没人等——机器死掉后单子只会一直贴着「本机做」。
3. **子任务没有登记处。** `node_sessions` 是自由格式的整份快照，今天的调用方（本仓以外）写什么字段都行，没有"这行属于哪张父单、是什么状态、租约到什么时候"的约定。
4. **接手没有凭据。** 分支名、head、最后一条进度分散在 GitHub 分支、本机收件箱、笔记账本三处，而且都不带"这是谁的活、做没做完"。
5. **失效后没有停写。** 领活用 token 做 fence，`renew` 不校验 token（**按代码** `nodeClaims.apply`），所以旧机器即使被接管，也不会从续期结果里学到"你已经不是持有者"。

## 三、逐个问题的选项和推荐

### 3.1 一个机群谁协调，管几个仓

先把两件事分开：

- **租约表**：当前任期内唯一的互斥依据，只保存「哪台机器以第几次尝试持有哪件活、何时到期」。协调者所在机器同时持有它。
- **协调者会话**：人只跟协调者对话、由协调者拆活和派活的普通 T3 会话。它消费租约表，不是另一份任务真相，也不因换了协调者就搬会话事件。

| 选项       | 做法                                                                                                         | 好处                                                       | 代价                                                       |
| ---------- | ------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------- | ---------------------------------------------------------- |
| 甲（采用） | 一个机群一个协调者，管该机群所有仓；租约键为 `repo + issue + taskId`，根任务 `taskId=root`，子任务用稳定子号 | 跨仓天然不冲突；仓只是看板筛选条件；只有一套角色和租约协议 | 协调者是不可用时的新领单点                                 |
| 乙         | 每个仓各选一个协调者                                                                                         | 单仓可独立切换                                             | 备选，未采用：同机群多角色、多会话，跨仓父子活要追多个任期 |
| 丙         | 不设协调者，各机靠标签和本地租约                                                                             | 没有角色切换                                               | 备选，未采用：标签非原子、无过期，仍会同领，不能发现中断   |

采用甲。**直接回答多仓疑问**：协调者管机群内所有仓，不只当前仓；`repo + issue + taskId` 决定互斥范围，所以不同仓、同仓不同单、同单不同子任务互不抢锁。同一个 `(repo, issue, taskId)` 才互斥。公司和个人要隔离时建两个机群，各有一个协调者，不按仓拆协调者。

「真相在执行机器上」只指本机会话是否仍活着、持有哪些 attempt、最后本地进度；**当前任期内谁能领单，真相仍是协调者租约表；最终结果仍在 GitHub 单、分支和 PR**。三者不能混成一句「都是真相」。

### 3.2 随时切换、交出协调者，任期怎么算

| 选项       | 做法                                                                                                            | 好处                                                            | 代价                                                                         |
| ---------- | --------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| 甲（采用） | 手动指定；带递增 `term`，在线交出由旧协调者分配下一号，强制接管取已知最大号加一；执行机向新协调者重登记，不搬库 | 随时可换；离线机回来按较大 `(term, coordinatorId)` 收敛；机制小 | 分区里强制接管不能靠算法证明只有一个协调者，只能靠任期收敛和写前确认降低风险 |
| 乙         | 把旧协调者的 SQLite 文件复制到新机器                                                                            | 看似保留完整状态                                                | 备选，未采用：复制期间旧机仍可写，文件不是互斥协议；路径和库版本也耦合       |
| 丙         | 自动选举、共识和复制账本                                                                                        | 无人接管且可抗分区                                              | 备选，未采用：新实现共识、成员变更和复制，远超当前规模                       |

采用甲，**第一期不做自动选举**。任期号只用于协调者角色；每件活另有单调递增的 `attempt/fencing`，两者不复用。每台机器只持久化很小的 `{fleetId, term, coordinatorId}` 角色元数据，不另建工作账本。

切换协议：

1. 在线交出：旧协调者把 `term+1` 和目标准备好的确认发给各在线机器，随后先停止领、续、还，再让目标开始服务；每条在跑的租约保留原 `taskId + attempt + fencing`，由执行机重登记。
2. 在本机点「设为协调者」：若旧协调者可达，走同一条在线交出；不可达时强制接管只要求一次确认框，不要求先人工确认旧机已停或隔离，再取已知最大 `term+1`。
3. 新角色经机器互连的身份、路由和令牌发送角色 RPC。这里**修正「现有 WebSocket 直接广播」的说法**：`PeerLinks` 当前是定向的 `/mcp` 客户端调用，不是服务端 WS 广播（**按代码** `docs/internals/remote.md:70-77`）；要新增很薄的 fleet 控制 RPC，但复用现有连接解析和鉴权，不另做机器发现。
4. 在线机器收到更高任期就持久化并停掉旧角色；离线机器回来时，任何角色 RPC、心跳响应或看板连接里的更高 `(term, coordinatorId)` 都让它切换。相同 `term` 用 `coordinatorId` 确定次序，只为最终收敛，不把同时强制接管变成安全选举。
5. 新协调者收重登记时保留有效 attempt；没报来的行只等原到期时刻，不立即重派。旧协调者恢复后先比任期，低任期不得接受领续还。

边界必须写死：两台被分区且都被强制接管的机器，在彼此看见之前可以各自发租约；手动任期不是共识。第一版接受这个残余竞态，用「各机器只认最大任期、旧协调者回来后自动让位」加每次 GitHub 写前确认收敛，不宣称数学上的单主。要消灭这个前提只能上丙。

### 3.3 租约、按机心跳，协调者挂了哪些活能干

| 选项       | 租约 / 心跳 / 失败策略                                                          | 好处                                                          | 代价                                                              |
| ---------- | ------------------------------------------------------------------------------- | ------------------------------------------------------------- | ----------------------------------------------------------------- |
| 甲（采用） | 90 秒 / 30 秒；所在机器 ADE 一条心跳批量续本机全部 issue 租约；服务端时钟判到期 | 一台机器每 30 秒一个小请求；一次抖动不打断；90 秒内可发现失联 | 协调者不可用时不能领新单，外部写要暂停                            |
| 乙         | 10 分钟 / 60 秒，仍按机批量                                                     | 更抗长抖动                                                    | 备选，未采用：中断发现慢 10 分钟                                  |
| 丙         | 每个会话各自续期，保留 2 小时                                                   | 调用方改动少                                                  | 备选，未采用：会话等待/回收就误断；请求随会话数增长；发现中断过慢 |

采用甲。**直接回答「其他机器是不是非得经协调者」**：不是。没挂 GitHub 单的随手活照常在本机开、跑、push 和开 PR，只把摘要报上看板；要领一张单才向当前协调者请求一次租约。协调者联系不上时，随手活不受影响，已领单可继续本地编辑和测试，但新领单等待恢复或手动换协调者；不做「先本地领、事后对账」。

心跳与快照分离：心跳只含 `{fleetId, term, ledgerEpoch, nodeId, leases:[{repo,issue,taskId,attempt,fencing}], clientRevision}`，协调者在一个事务里逐条条件续期，响应逐条给 `ok / not_claimed / stale_term / retry`。不含标题、日志和 diff。摘要另走变化推送（3.6）。

- 单次超时只是「结果不确定」，不能当未领，也不能立刻重新领；下个周期带同一 attempt 查询并续。只接受匹配当前请求序号、term 和 ledgerEpoch 的响应；晚于一个心跳周期的 200 按失败处理，不能重新获得完整写闸窗口。
- 连续 30 秒没有确认，标记「续期未确认」，暂停该 attempt 的外部写；本地工作继续。401（撤销）、明确 `not_claimed` 或更高 attempt 已接管才停止对应会话；503/超时只停写，不误判已被接管。
- 到期只由协调者服务端时钟判定；客户端用单调时钟测距上次有效确认的时间，不用本机墙钟判租约失效。协调者时钟异常向前跳时暂停自动接管。
- 老 HTTP 调用方可保留 2 小时 legacy 租约，但不能参与新自动接管；新旧客户端不得在同一机群混领。升级先 drain 旧模式，再一次性切到唯一协调者路径。

验收：断网 60 秒，本机随手活和已领活都能本地继续，另一台领不到这张单，push/PR 被写闸挡住；断到 90 秒后另一台才可接，旧机下一次续期得到拒绝。

### 3.4 父子任务登记和只重派一个

| 选项       | 权威记录                                                                                                                  | 好处                                                      | 代价                                                                                      |
| ---------- | ------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 甲（采用） | 扩展唯一 `node_claims`：加 `taskId,parentTaskId,attempt,environmentId,threadId,branch,headSha,status`，父子都在同一租约表 | 不建第二张父子表；每个子任务独立租约、独立 fencing 和重派 | 现有键和写入协议要迁移                                                                    |
| 乙         | 新建 `pipeline_children` 持久表，租约仍放 `node_claims`                                                                   | 查询直观                                                  | 备选，未采用：两份权威状态要事务同步，违背不建持久账本                                    |
| 丙         | 用 `node_sessions` 快照当父子真相                                                                                         | 表面改动少                                                | 备选，未采用：一机一行、整份覆盖、20 秒节流，没有单子任务事务和 attempt，正常并发就会覆盖 |

采用甲；**驳回用快照登记子任务**。快照仍可做展示缓存，不能当调度依据（**按代码** `nodeReads.ts:58-62,96-111`）。每个子任务键为 `(repo,issue,childTaskId)`，`parentTaskId` 指根或上级子任务；`attempt` 每次重派加一，旧 attempt 的终态和进度不能覆盖新 attempt。

- 协调者会话经 `RemoteDelegation` 派到目标环境，记录返回的 `environmentId/threadId`；远端跟随者已有重启续跟（**按代码** `docs/internals/remote.md:133-140`）。
- 子任务中断只让该 `taskId` 的旧 attempt 到期并创建新 attempt；兄弟和父活不动。父活自己失联才接根租约，再接当前子任务清单。
- `completed` 不重派；`failed/interrupted/cancelled` 或租约丢失才进入该子任务的重派判定。`SessionEndInbox` 只提供执行机本地终态和 head（**按代码** `SessionEndInbox.ts:24-38`），不是跨机父子账本。

### 3.5 接手凭什么，怎么避免双写和双 PR

接手输入仍是**已推送分支 + 最后一条进度**：有分支就从该 head 接；只有笔记就从基线重做并带笔记；都没有转人。笔记是恢复线索，不是写授权。

| 选项       | 外部写策略                                                                                                                                         | 好处                                                                  | 代价                                                                                              |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| 甲         | 每次重派新 attempt、新分支；push 和开 PR 前即时向协调者确认当前 `term+attempt+fencing`；禁 force-push；PR 创建按 attempt 幂等，旧 PR 标 superseded | 新旧执行者不写同一分支；写前拒绝不依赖「30 秒内续过」；改动集中在 ADE | 备选，未采用：旧机仍能在自己 attempt 分支写入，且要额外维护旧 PR superseded；残余竞态没有实质减少 |
| 乙         | 所有 GitHub 写都过受控代理，代理校验 fencing                                                                                                       | 外部写入口真正收束                                                    | 备选，未采用：新部署和凭据边界，维护成本最大                                                      |
| 丙         | 只靠租约和最近 30 秒心跳，直接推同一分支                                                                                                           | 最少代码                                                              | 备选，未采用：GitHub 不认识 SQLite fencing；丢库、乱序和旧机复活会双写                            |
| 丁（采用） | 一件活（含子任务）固定一条确定分支；接手从已推送处接着做，只允许快进推送；一条分支只认一个 PR；外部写之前仍向协调者确认租约还在手里                | 分支名和 PR 归属确定；旧机恢复后的非快进推送被 Git 拒绝；实现最少     | 同一秒两边开 PR 的残余竞态靠「一条分支一个 PR」和幂等查询收敛，不能承诺零竞态                     |

采用丁，但明确它是**降低并收敛双写，不是强 fencing**。`fencing` 能拒绝经过租约表的旧请求，不能撤掉旧机器已经拿到的 GitHub 凭据。即时 authorize 后若恰遇接管，旧机仍可能写入；确定分支、快进推送限制和「一条分支一个 PR」负责收敛。若要求外部写也严格互斥，只能选乙。

写前确认覆盖 ADE 自动 push、开 PR、单评论/标签和跨机派子任务；不能只看 pipeline 的两个显式调用点。用户或 agent 若直接用机器上已有凭据绕过 ADE，本方案无法收回在飞请求，这也是不宣称端到端零双写的原因。

所有领、续、还、派子任务和开 PR 都要有幂等键或可查询结果；超时先查，不重复开 PR/派子任务。接手方禁止复用旧机器工作树，禁止 force-push；已推送的远端 head 是接手基线。`t3_thread_wait` 的 50 秒上限只是一次等待超时，不是子任务失败或重派条件。

### 3.6 看板、实时订阅和性能

| 甲（采用） | 看板打开时连当前协调者的摘要 WS；先全量小快照，再按 `revision` 只推变化；详情按需直连执行环境现有 `subscribeThread` | 汇总只有摘要，会话正文不过协调者；连接数与打开的页面成正比 | 要新增 fleet 摘要契约和游标重同步                                    |
| 乙         | 每台机器向每台机器推全量会话和事件                                                                                  | 无中心页面                                                 | 备选，未采用：N×N 数据和连接，随日志持续增长                         |
| 丙         | 续期响应捎带看板增量                                                                                                | 少一条订阅                                                 | 备选，未采用：无租约的随手活收不到；断一次就缺口；心跳协议和 UI 耦合 |

采用甲，**驳回续期响应捎带看板**。现有客户端已经能同时连接多个环境，详情直接连拥有会话的环境（**按代码** `docs/internals/remote.md:148-153`）；现有 WS 有壳和单会话订阅，但没有全网租约摘要，所以只加摘要契约，不复制会话事件。

看板摘要一行只有 `{fleetId,repo,issue,taskId,attempt,environmentId,status,title,lastProgress,branch,headSha,updatedAt}`；随手活 `issue=null`、无租约字段。每行有 `revision`，断线从游标续，缺口或版本不连续就重拉一次全量小快照。摘要有界：只含当前打开的活和最近终态，不传消息正文、工具输出、diff。

流量上界：N 台机器每 30 秒各一条批量心跳，即 **2N 请求/分钟**，与租约数无关；看板无变化不推，变化只推改动行。一个浏览器只看板时一条到协调者的摘要连接；点开详情才增加到执行环境的一条会话订阅，关闭详情即退订。协调者会话页只在打开时订那条会话。容量验收按 N=20、每机 50 个子任务：心跳仍 40 请求/分钟，1000 行仅注册和续期，不推 1000 条会话事件。

### 3.7 协调者会话页和看板入口、反向操作

| 选项       | 会话归属和切换后的处理                                                     | 好处                                     | 代价                                                              |
| ---------- | -------------------------------------------------------------------------- | ---------------------------------------- | ----------------------------------------------------------------- |
| 甲（采用） | 每个协调者任一条普通 T3 会话；换协调者开新会话，带上一任的摘要和旧会话链接 | 不搬线程、不复制事件；执行仍在协调者环境 | 跨任期不是同一会话，旧讨论通过链接查看                            |
| 乙         | 换协调者后继续操作旧机器上的同一线程                                       | 对话表面连续                             | 备选，未采用：控制者在新机、会话仍在旧机，旧机挂时页面也挂        |
| 丙         | 把旧线程全量复制到新环境                                                   | 看似完整迁移                             | 备选，未采用：事件 id、权限和执行状态都要合成，制造第二份会话真相 |

采用甲。T3 的线程属于一个环境和项目（**按代码** `docs/internals/remote.md:13-15`），所以「机群唯一会话」是一个逻辑入口，不是跨机移动线程。会话创建时仍选一个协调者环境里的项目作为宿主；跨仓派活由 fleet 服务和远程环境工具完成，不被宿主项目限制。

界面入口和反向操作：

- **机群看板**：主导航增加「机群」；环境选择器也提供「打开机群看板」。页头显示当前协调者、任期、连接状态；仓、机器、状态只是筛选器。
- **协调者会话页**：看板页头「打开协调者会话」，环境行的协调者标记也可进入。任何机器上的客户端都通过已保存的远程环境连接打开同一条当前任期会话；输入框只发给当前协调者，不再选执行环境。看板顶部固定显示这条会话的状态和最后进度，离开详情页即退订正文。
- **设为协调者**：非协调者环境行提供此操作；旧机可达时走在线交出，不可达时显示一次确认框，确认后以更大任期接管。成功后入口切到新会话，旧会话保留只读链接。
- **交出协调者**：仅当前协调者显示，选择目标机器后走在线任期切换；不是删会话、不停止在跑的执行机。没有目标的「关闭协调」第一版不提供，避免全机群失去领单入口。
- **看板行**：点「查看」直连执行机看会话；有权限时可「停止」该 attempt 或「重派」已中断子任务。随手活只能停止自己的会话，不能伪造一张已领租约。

桌面和 web 共用上述页面；移动端复用同一摘要和命令契约。agent 不读 UI 状态，走同一 fleet 服务方法；远程/隧道只改变路由，不改变任期和租约语义。

### 3.9 协调者重启、丢库后怎么恢复

| 选项       | 恢复方式                                                                                                                                                 | 好处                                                        | 代价                                                          |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------- |
| 甲（采用） | 库完整就从现有行恢复；库为空/损坏/回滚备份则提升 term、换 `ledgerEpoch`，进入 150 秒恢复窗，只收执行机重登记、不发新 attempt，所有外部写确认 fail-closed | 正常重启无感；旧 epoch 的租约请求全部失效；无需持久事件账本 | 丢库后新领和接管暂停 90 秒租约加 60 秒外部写在飞上限          |
| 乙         | 重启后一律当空表，各机边跑边重新领                                                                                                                       | 恢复最快                                                    | 备选，未采用：新旧 attempt 可并存，旧机本地写闸可能仍认为有效 |
| 丙         | 多副本持久账本和自动选主                                                                                                                                 | 可自动抗丢库                                                | 备选，未采用：回到共识系统，超出第一版                        |

采用甲。这里的「不建持久账本」指不复制 GitHub 工作历史、不建事件溯源账本；现有 SQLite 仍是可重建的实时租约存储，角色 `term`、`ledgerEpoch` 和机器通行证必须持久化。`term` 标识协调者角色，`ledgerEpoch` 标识一份账本生命周期，二者不能复用。整个状态目录丢失时，该机不得自动以旧协调者身份起来，要人工重新「设为协调者」并提升任期、生成新 epoch。

恢复窗内原 holder 用原 attempt/fencing 加上新 epoch 重登记，重复登记幂等；其他机器不能抢。恢复窗固定 150 秒（90 秒租约加 60 秒 ADE 外部写超时上限）；结束仍未登记的行才过期。所有 claim/renew/authorize 都校验 epoch，旧备份、旧进程和迟到响应不能借旧 fencing 复活。任何续期响应丢失都先查询确认；库写失败、磁盘满、锁超时返回 503，不返回空表，不接受新领。

## 四、推荐方案连起来走一遍

1. 一个机群登记多台环境和多个仓；A 是当前协调者，`term=7`，同时有一条协调者会话和唯一租约表。
2. B 的随手活不领租约，只上报一条摘要；B 要领 `repo1#N`，向 A 请求 `root` 租约，拿到 `attempt=1` 和 fencing。
3. B 每 30 秒把本机所有 issue 租约放在一条心跳里续；`repo2#M` 的行键不同，不与 `repo1#N` 冲突。
4. 人在任一机器打开「机群」，只连 A 的摘要流；打开协调者会话，就连 A 上当前任期的普通会话。协调者拆出两个子任务，各自登记租约并经互连派到 B、C。
5. C 的一个子任务挂掉：只有该 `taskId` 的租约到期，新 attempt 从已推分支和最后进度接；另一个子任务和父活不动。
6. A 在线时交出：页头选 B，A 分配 `term=8`，B 接任，各执行机重登记原 attempt，协调者会话入口切到 B 的新会话。
7. A 死机时：人在 B 点「设为协调者」，确认 A 已停止或隔离，强制进入 `term=8`。离线 A 若回来，看到更高任期后只做执行机。
8. 协调者不可用期间，随手活照常，新领单暂停；已领活可本地继续，push/PR 等写前确认恢复。

## 六、业界对照、风险和回滚

业界对照：

- [Kubernetes Leases](https://kubernetes.io/docs/concepts/architecture/leases/) 用节点心跳的 `renewTime` 判可用，也用 Lease 做领导者选举。本稿采纳「心跳刷新、到期才判失联」，但把工作租约按键拆开、按机器批量发送，不照搬每会话一个对象。
- [Raft 官方概览](https://raft.github.io/) 明确共识解决多台服务器对同一值达成一致，并在多数不可用时停止推进。本稿不做自动选举；手动 `term` 只提供角色代次和最终收敛，**不能冒称 Raft 的分区安全性**。

主要风险：

- **强制接管的分区**：任期不是共识；一次确认强制接管只把人工步骤减到最低，被分区机器在彼此看见前仍可能双主。要绝对安全只能引入共识或受控 Git 写代理。
- **GitHub 不认 fencing**：即时确认 + 确定分支 + 快进推送 + 一条分支一个 PR 只负责收敛；存在 authorize 后、push/PR 前的竞态，稿中不保证零双写。
- **协调者兼执行机**：磁盘满和锁竞争会同时影响执行和租约。心跳事务必须短，摘要不进同一长事务；503 时 fail-closed。
- **互连方向和有效期**：PeerLinks 是定向的；机群控制需要目标方向已有链接。角色切换前应显示不可达机器，不能写「广播成功」。
- **升级双模式**：本地直写与协调者模式不能同时领同一机群的单；先 drain 再切。

回滚按功能关闭：先停自动接手，再隐藏新页面，最后停止自动领单。不能回退成「本机标签也是一把锁」；那样会重新引入双领。

## 七、没核实的

- 没连正在跑的服务，没实测真实机器互连、路由、证书和隧道可用性；#140 的互通前置仍未拍板。
- 没实测 N=20、每机 50 个子任务下的 SQLite 写入时延和 WS 帧大小；第五节的数量是设计验收上界，不是性能实测。
- 没核实外部 `/api/nodes/claims` 调用者名单；legacy 兼容边界要在实施前盘点。
- 没做界面视觉稿；本节只定信息架构、入口、反向操作和数据流，实施界面时再给目标尺寸截图。
- 没证明即时 authorize + 确定分支能完全消灭 GitHub 竞态；本稿明确保留同一秒两边开 PR 的残余竞态，靠「一条分支一个 PR」和幂等查询收敛。

## 九、拍板结果

| #   | 事           | 结论                                                                                          | 理由                                                                                        |
| --- | ------------ | --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------- |
| 1   | 协调范围     | 一个机群一个协调者，管所有仓；租约键 `repo + issue + taskId`                                  | 不同仓和同仓不同单天然不冲突，仓只是看板筛选；只有一套角色                                  |
| 2   | 切换协调者   | 手动任期；在线交出分配 `term+1`；不可达时一次确认强制接管；各机器只认最大任期                 | 机器少且都在同一控制者手里，再多一道人工停机/隔离确认换不来足够安全；离线机回来自动让位     |
| 3   | 租约与心跳   | 按机器批量心跳 30 秒；90 秒没心跳算断；随手活不经协调者，协调者不在时新领单暂停               | 流量按机器计而非会话计；一次网络抖动不误断；随手活不受协调者可用性影响                      |
| 4   | 子任务真相   | 扩展现有租约表；子任务各一行、各有 attempt，只重派断掉的那个                                  | 不建第二份父子账本；每个子任务有独立 fencing 和状态                                         |
| 5   | 外部写与接手 | 一件活固定一条确定分支；接手从已推送处接着做，只允许快进推送；一条分支一个 PR；写前仍确认租约 | 分支名和 PR 归属确定；旧机恢复后非快进推送被 Git 拒绝；残余竞态靠唯一分支/幂等收敛          |
| 6   | 看板数据     | 摘要先全量小快照再按 revision 推变化，带游标；缺口时全量重同步；详情点开才直连执行机          | 摘要流量随变化行增长，不随日志增长；正文不经过协调者                                        |
| 7   | 协调者会话   | 每个任期新开协调者会话，带上一任摘要和链接                                                    | 线程仍属于一个环境；不搬事件、不复制会话真相                                                |
| 8   | 现有写路径   | 机群内只有协调者写租约表；升级先等在跑的活做完再一次切换，不留本地/协调者双模式               | 避免滚动期间双账本和双领；单一写入口能条件更新和 fencing                                    |
| 9   | 重启恢复     | 库在就直接恢复；库丢了换 `ledgerEpoch`，等 150 秒让各机器重新登记，期间不发新租约             | 正常重启无感；旧备份、旧 epoch 和迟到响应不能复活；恢复窗与 90 秒租约加 60 秒外部写超时一致 |

未采用但保留的备选：每仓一个协调者、复制 SQLite、自动选举/共识、10 分钟租约、每会话 2 小时租约、新父子表、快照真相、attempt 新分支、受控 Git 代理、只靠心跳、N×N 全量互推、心跳捎带看板、跨任期复用或复制线程、双写路径、空表立即重领。原因分别留在 3.1–3.9。
